# 仕様書 → 型安全テストケース変換スキル

## 1. 入力の解析とプロジェクト環境の調査

### 入力の取得
引数 `$ARGUMENTS` に応じてソースを取得する：
- **ファイルパス:** `Read` で内容を取得。
- **URL:** `WebFetch` でコンテンツを抽出。
- **Jira番号:** `jira` CLI または API で取得を試みる。失敗時はユーザーに内容のペーストを依頼する。

### プロジェクト環境の調査（仕様整理の精度を高めるため、先に実行する）
1. **フレームワーク特定:** `package.json` 等から Jest, Vitest, Playwright, Cypress 等を特定。
2. **型定義の探索:** 関連する `interface`, `type`, `schema` ファイルを `Glob` で探し `Read` する。
3. **既存テストの流儀:** 既存の `*.test.ts` を1つ読み込み、モックの作り方・命名規則・assertion スタイルを把握する。
4. **モック戦略の把握:** 既存テストで使われているモック手法（MSW, nock, jest.fn, Repository モック等）を確認する。

## 2. 仕様の整理と構造化

読み込んだ内容を以下の項目で整理し、ユーザーに提示する：

### 機能概要
- 何を実現する機能か、ビジネス価値は何か。

### 前提条件
- 実行に必要なデータ状態、認証、フラグ等。

### 正常系 / 異常系 / 境界値
- 期待される振る舞いを箇条書きで整理。

### 考慮漏れ・エッジケースの指摘
- 仕様書に記載がないが、フルスタック視点で不可避なケース（通信失敗、タイムアウト、権限不足、データ競合、非同期の完了保証等）を指摘する。
- 副作用・事後条件を確認する（DB にレコードが作成/削除されるか、外部ストレージの状態、他機能への影響等）。

### 仕様と既存コードの不整合
- 仕様書の内容が既存の型定義・DB スキーマ・API 定義と矛盾している場合、「不明点・確認事項」として報告する。

### 非機能要件（あれば）
- パフォーマンス、セキュリティ等。計測可能な場合のみ記載する。計測可能な非機能要件が存在する場合はテストケースを必ず作成する。

### 不明点・確認事項
- 推測を排除し、ユーザーに判断を仰ぐ項目。

**不明点が1つでも存在する場合、テストケース生成を禁止する。仮定で進めることを禁止する。**
**ユーザーの承認を得るまで次へ進まない。**

## 2.5. テストレベルの決定

ユーザーと合意した仕様に基づき、テストレベルを明示的に選択する：

| レベル | 対象 | 例 |
|---|---|---|
| **Unit** | 関数・クラス単位 | バリデーション関数、計算ロジック |
| **Integration** | API / DB を含む結合 | エンドポイント、リポジトリ層 |
| **E2E** | UI を含む一連のフロー | ログイン→購入→決済 |

デフォルトは **Integration** とする。不明な場合はユーザーに確認する。

## 3. テストケース（シナリオ）の作成

承認された仕様に基づき、テストケース一覧を生成する。

テストケース ID: `TC-<機能>-<番号>`（例: `TC-AUTH-LOGIN-01`）
優先順位: 正常系 → 異常系 → 境界値 → エッジケース。

```
- [ ] TC-AUTH-LOGIN-01: [正常系] 正しい認証情報でログインすると、トークンが返されること
- [ ] TC-AUTH-LOGIN-02: [異常系] 不正なパスワードでログインすると、401 エラーが返ること
- [ ] TC-AUTH-LOGIN-03: [境界値] パスワードが最大長の場合でもログインできること
- [ ] TC-AUTH-LOGIN-04: [エッジケース] 認証サーバー通信失敗時に適切なエラーが返ること
```

**ユーザーの承認を得るまで次へ進まない。**

## 4. 型安全なテストコードの生成

### コード品質ルール
- **型準拠:** 調査した既存の型定義をインポートし、型エラーのないコードを書く。
- **AAA パターン:** Arrange（準備）, Act（実行）, Assert（検証）をコメントで明示。
- **1テスト1関心:** 同一の振る舞いに対する複数 assertion は許容するが、異なる関心を1テストに混ぜない。
- **独立性:** テストデータはテスト内で完結させる（Factory 関数等の利用）。テストは並列実行される前提で設計し、グローバル状態の共有や実行順序への依存を禁止する。
- **既存の流儀に従う:** ステップ1で把握した既存テストの命名規則・モック方法に揃える。
- **実装前考慮:** 実装が未完了でもインターフェースが定義されていればそれに合わせる。テストが実行できなくても OK。

### モック・テストダブル方針
- **外部 API:** モック（プロジェクトの既存手法に従う。未定の場合は MSW を推奨）
- **DB:** Repository 層をモック（Integration テストで実 DB を使う場合はその旨を明記）
- **時間依存:** fake timers を使用
- **ランダム値:** seed 固定またはモック化

### テストの書き方
- テスト名は「何が起きるか」を明示する（既存テストの命名規則に合わせる）
- assertion には意図が分かるメッセージを付与する

## 5. 最終出力

1. 整理済みの仕様（ステップ2の結果）
2. テストレベル（ステップ2.5の結果）
3. 承認済みテストケース一覧（ステップ3の結果）
4. 生成されたテストコードのファイルパス

## ルール
- 仕様が曖昧な箇所は推測せず、ユーザーに確認する
- 不明点が残っている状態でテストケース・テストコードを生成してはならない
- テストの優先順位: 正常系 → 異常系 → 境界値 → エッジケース
- 非機能要件が計測可能な場合はテストケースを必ず作成する
- ユーザーの確認ステップを飛ばしてコードを生成してはならない
